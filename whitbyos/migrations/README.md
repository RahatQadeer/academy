# Whitby migrations

SQL owned by the Whitby module, kept here rather than in `/supabase/migrations`
because that folder is shared and Laiba owns it.

**Nothing in here is applied automatically.** These files are written, reviewed
with Laiba, and only then folded into the shared migration set. Treat them as
proposals until that happens.

## Why this folder exists

`/supabase/migrations` is the single source of truth for the whole ecosystem —
four people's tables live there and it must stay one coherent, ordered history.
Editing it directly from a module branch would put four people in conflict over
the same files. So Whitby-owned SQL is drafted here, reviewed, and merged there
by its owner.

## Conventions

**Policy names end in `_staff`.** Postgres combines multiple policies on a table
with `OR`, so the Client Portal can add its own `_client` policies to the same
tables later and both will apply. Neither side has to drop or edit the other's.

**Every file is safe to re-run.** Each policy is dropped by its own name before
being created, so nothing pre-existing is touched and running twice is harmless.

**Access is granted through `public.is_workspace_member()`**, the helper the
already-working Whitby tables use. Rows are reachable by active members of the
workspace that owns the row's parent — usually via its Request.

## Background

30 of the 69 tables in the shared schema have `enable row level security` with
no policy at all. Postgres then denies every read and write, so those tables
return zero rows with no error — it reads as an application bug until you check
the migration. 16 of them are Whitby's; the rest belong to Academy and Partner
Center, whose owners will need the same treatment.
